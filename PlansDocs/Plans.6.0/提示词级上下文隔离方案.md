# 提示词级上下文隔离方案

> 状态：待复核\
> 日期：2026-07-30\
> 关联：V10\_\_memory\_prompt\_scoped（记忆层 prompt\_id 隔离，已完成）

***

## 一、背景与目标

### 1.1 现状

V10 迁移已实现记忆层（`memory_items`）的 prompt\_id 隔离：

- `prompt_id = NULL` → 共享记忆，所有提示词可见
- `prompt_id = 非NULL` → 私有记忆，仅该提示词可见

但上下文构建中以下三层**不做 prompt\_id 隔离**，导致同会话切换提示词时上下文污染：

| 层                   | 当前隔离状态          | 问题                                  |
| ------------------- | --------------- | ----------------------------------- |
| MemoryItem          | 已隔离             | 无                                   |
| Conversation        | 无 prompt\_id    | 同一会话可混用多个提示词                        |
| ChatMessage         | 无 prompt\_id    | 切换提示词后，新提示词的 LLM 能看到旧提示词的全部历史消息     |
| ConversationSummary | 跟随 Conversation | 摘要混杂了不同提示词的对话内容                     |
| 知识图谱（实体/关系）         | 用户级共享（设计如此）     | 图扩展反查记忆时未过滤 prompt\_id，可能泄露其他提示词的记忆 |

### 1.2 目标

将私有/共享模式从记忆层下沉到会话层、消息层、摘要层和图扩展层，确保**不同提示词拥有独立的上下文，避免交叉污染**。

***

## 二、数据库变更

### 2.1 conversations 表

```sql
ALTER TABLE conversations ADD COLUMN prompt_id BIGINT NULL;
ALTER TABLE conversations ADD INDEX idx_user_prompt (user_id, prompt_id);
ALTER TABLE conversations ADD FOREIGN KEY (prompt_id) REFERENCES prompts(id) ON DELETE SET NULL;
```

| prompt\_id | 语义           |
| ---------- | ------------ |
| NULL       | 共享会话，所有提示词可见 |
| 非NULL      | 私有会话，仅该提示词可见 |

### 2.2 chat\_messages 表

```sql
ALTER TABLE chat_messages ADD COLUMN prompt_id BIGINT NULL;
ALTER TABLE chat_messages ADD INDEX idx_conversation_prompt (conversation_id, prompt_id);
```

记录每条消息发送时使用的提示词，用于上下文注入时的过滤。私有会话中所有消息的 prompt\_id 一致；共享会话中消息的 prompt\_id 可能混杂。

### 2.3 conversation\_summaries 表

**不做结构变更。** 摘要跟随 Conversation 的隔离：

- 私有会话的摘要天然只包含该提示词的消息
- 共享会话的摘要包含所有提示词的消息（符合"共享"语义）

## 三、后端改动

### 3.1 Conversation 模型

```java
// Conversation.java 新增字段
@Column(name = "prompt_id")
private Long promptId;
```

### 3.2 ChatMessage 模型

```java
// ChatMessage.java 新增字段
@Column(name = "prompt_id")
private Long promptId;
```

### 3.3 会话创建 API

`POST /api/conversations` 请求体新增可选字段：

```json
{
  "promptId": 1   // 可选，null 表示共享会话
}
```

ConversationService 创建会话时写入 prompt\_id。

### 3.4 ChatService — 消息保存

`ChatHistoryService.saveMessage()` 写入 `chat_messages` 时，记录当前的 `promptId`（从 `ChatRequest.promptId` 获取，若会话已绑定则与会话的 prompt\_id 一致）。

### 3.5 MessageContextBuilder — 历史消息过滤

构建上下文取最近 30 条历史消息时，增加 prompt\_id 过滤：

```sql
SELECT * FROM chat_messages
WHERE conversation_id = :conversationId
  AND (prompt_id IS NULL OR prompt_id = :currentPromptId)
ORDER BY timestamp DESC
LIMIT 30
```

逻辑：

- 当前提示词的 prompt\_id 为 NULL 时 → 只取 prompt\_id IS NULL 的消息（共享消息）
- 当前提示词的 prompt\_id 为 X 时 → 取 prompt\_id IS NULL OR prompt\_id = X 的消息

### 3.6 GraphMemoryService.expandViaGraph — 图扩展过滤

**实体和关系保持用户级共享，不做 prompt\_id 标记。** 隔离发生在图扩展最后一步——从实体反查记忆时：

```
expandViaGraph(seedItemId, maxResults, promptId):
  种子记忆 → 关联实体
    → 同实体的其他记忆 WHERE (prompt_id IS NULL OR prompt_id = :promptId)
    → 沿关系找邻接实体
      → 邻接实体的记忆 WHERE (prompt_id IS NULL OR prompt_id = :promptId)
```

当前方法签名需新增 `promptId` 参数，在调用 `itemEntityRepo.findMemoryIdsByEntityId()` 后查询 `memoryItemRepo` 时，增加 prompt\_id 条件过滤。

调用链穿透：

- `MemoryService.getRecentMemoriesForContext(userId, promptId)` → 已有 promptId
- `MessageContextBuilder` 调用图扩展时传入 promptId

### 3.7 MemoryItemRepository — 新增图扩展查询方法

新增专用查询，支持从实体反查记忆时过滤 prompt\_id：

```java
@Query("SELECT m FROM MemoryItem m WHERE m.id IN :ids AND m.enabled = true AND m.status = 'ACTIVE' AND (m.promptId IS NULL OR m.promptId = :promptId)")
List<MemoryItem> findByIdInAndPromptAccessible(@Param("ids") List<Long> ids, @Param("promptId") Long promptId);
```

### 3.8 会话列表 API

`GET /api/conversations` 返回全部会话（不做 prompt\_id 过滤，用户需要看到所有会话记录）。每条会话返回 `promptId` 和 `promptName`（JOIN prompts 表），供前端侧边栏展示提示词标签。

### 3.9 ChatRequest.promptId — 改为后端读取

**改造前**：前端通过 `ChatRequest.promptId` 传入当前使用的提示词 ID

**改造后**：前端不再传 `promptId`（或忽略该字段）。后端 `ChatService` 直接从会话记录中读取 `conversation.prompt_id`，用于：

- 消息保存时写入 `chat_messages.prompt_id`
- 记忆提取时传入 `MemoryService.extractAndStore(..., promptId)` 的 promptId 参数
- 上下文构建时传入 `MessageContextBuilder.buildMessagesArray(..., promptId)`

ChatRequest 中 `promptId` 字段可保留但标记为 `@Deprecated`，或直接移除（需同步改前端）。

## 四、前端改动

### 4.1 核心思路

**"选择并应用提示词"的职责从 PromptModal 剥离，完全交给新建会话流程。** PromptModal 回归纯粹的 CRUD 管理工具。提示词信息从 Header 的 PromptIndicator 迁移到侧边栏会话条目上展示。

```
改造前：
  新建对话 → 空白页 → 中途 PromptModal 选择 → 切换提示词
  Header: [PromptIndicator 可点击切换]

改造后：
  新建对话 → 设置弹窗（名称 + 提示词） → 创建绑定会话
  Header: 无 PromptIndicator（移除）
  Sidebar: 每条会话显示提示词标签
  PromptModal: 仅管理（增删改查），不做选择
```

### 4.2 新建对话设置弹窗（NewConversationDialog）

点击侧边栏"新建对话"按钮 → 弹出设置弹窗，包含：

| 字段      | 类型    | 说明                                                          |
| ------- | ----- | ----------------------------------------------------------- |
| 会话名称    | 文本输入框 | 自定义名称，placeholder 为 "新对话"，可留空使用默认值                          |
| 提示词     | 下拉选择器 | 列出用户所有提示词，默认选项为"无（共享会话）"，选中后显示名称                            |
| 确认 / 取消 | 按钮    | 确认 → 调用 `POST /api/conversations` 传入 name + promptId；取消关闭弹窗 |

弹窗尺寸紧凑（如 400px 宽），居中显示，点击遮罩层可关闭。

下拉选择器的数据来源与 PromptModal 相同（`GET /api/prompts`），但以 Select/Dropdown 形式呈现，不再复用 PromptModal。

### 4.3 PromptModal — 纯管理模式

**移除所有选择相关功能：**

- 删除 `onSelectPrompt` 回调
- 列表项不再可点击选中


### 4.4 Header — 移除 PromptIndicator，保留管理入口

**移除 PromptIndicator 组件**（该组件不再需要）。

Header 右侧工具栏中的"提示词"图标按钮保留，点击打开 PromptModal（纯管理模式，仅查看/增删改）。

### 4.5 侧边栏会话列表 — 展示提示词标签

每条会话条目在原有标题下方或右侧显示一个小标签，表示该会话绑定的提示词：

```
┌──────────────────────────┐
│ 📝 工作讨论               │

├──────────────────────────┤
│ 📝 日常闲聊               │
│    共享会话               │  ← prompt_id=NULL 时显示
├──────────────────────────┤

```

会话列表 API 返回数据中需包含 `promptId` 和 `promptName`（JOIN prompts 或后端组装）。

### 4.6 App.tsx 状态调整

**移除** **`activePrompt`** **全局 state。** 提示词信息完全从属于当前会话：

```typescript
// 改造前
const [activePrompt, setActivePrompt] = useState<Prompt | null>(null);

// 改造后：不再需要此 state
// ChatRequest.promptId 从 activeConversation 对象中读取
// 发送消息时无需额外传入 promptId，后端从会话记录中获取
```

`ChatRequest.promptId` 的来源：

- 新建会话时已在弹窗中选定并随 `POST /api/conversations` 写入
- 后续发消息时，后端从会话的 `prompt_id` 字段获取，前端无需再传
- 或者前端仍传但仅作为校验，与后端会话的 prompt\_id 比对

**建议**：前端发消息时不再传 `promptId`，后端直接从会话记录读取。这样前端无需维护此状态，也杜绝了前端绕过隔离的可能。

## 五、知识图谱设计说明

### 5.1 实体层：用户级共享（不做 prompt 隔离）

**理由**：

- "张三"是同一个实体，不管用哪个提示词对话
- 不同提示词提取的关于同一实体的记忆，应能通过实体关联起来
- 实体消歧（合并）不应受 prompt 边界影响

### 5.2 关系层：用户级共享（不做 prompt 隔离）

**理由**：

- 关系是实体间的连接路径，是中性信息
- 即使关系来源于 Prompt A 的记忆，Prompt B 遍历实体时经过这条边也不构成泄漏——因为到达邻接实体后反查记忆时会被 prompt\_id 过滤
- 如果 Prompt B 在邻接实体上没有可见记忆，这条路径是死胡同

### 5.3 图扩展：仅在记忆反查时过滤

```
遍历路径：记忆 → 实体 → 关系 → 邻接实体 → 记忆（此处过滤 prompt_id）
                                                    ↑
                                              唯一隔离点
```

示例：

```
F1: "用户叫张三"     → prompt_id=NULL (共享)
F2: "张三在华为工作"  → prompt_id=A
F3: "张三住在北京"    → prompt_id=B

Prompt A 下图扩展：
  F2 → 实体"张三" → 同实体记忆 → F1(共享)✅ F3 被过滤✅
  F2 → 实体"华为" → 同实体记忆 → 仅有 A 的记忆

Prompt B 下图扩展：
  F3 → 实体"张三" → 同实体记忆 → F1(共享)✅ F2 被过滤✅
```

### 5.4 需要关注的情况

ChromaDB 搜索路径中旧记忆的反查也可能触及跨提示词记忆，需确认 `HybridRetrievalService` 和 `EntityRetrievalService` 中的实体匹配链路是否需要同步加 prompt\_id 过滤。

## 八、风险点

1. **兼容性**：现有会话的 `prompt_id` 为 NULL（共享），不影响已有数据
2. **前端状态复杂度**：`activePrompt` 从全局 state 变为跟随会话，需确保会话切换时状态正确更新
3. **图扩展性能**：新增 prompt\_id 过滤条件，需确认 SQL 查询计划走索引
