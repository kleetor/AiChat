# AI Chat 知识库与记忆系统详解

---

## 一、系统总览

本项目实现了一套完整的 **RAG 知识库** 和 **三层记忆** 双轨系统，底层共享 ChromaDB 向量数据库、SiliconFlow 嵌入模型与 Cross-Encoder 精排服务，上层通过不同 Collection 命名空间实现天然隔离。

| 维度 | 知识库系统 | 记忆系统 |
|------|-----------|----------|
| 定位 | 外部文档注入，提升回答专业性 | 用户长期画像，跨会话上下文延续 |
| 数据来源 | 用户上传的文档 | 对话过程自动提取 + 手动添加 |
| 生命周期 | 用户主动管理 (增删改查) | 自动衰减 + 用户手动干预 |
| 向量 Collection | `kb_{kbId}` | `mem_{userId}` |
| 检索方式 | 多查询重写 + RRF 融合 + Rerank | 语义+知识图谱双路 + RRF 融合 + Rerank |

## 二、知识库 (RAG) 系统

### 2.1 架构概览

```
用户上传文档 → 本地存储 → 异步处理管线
                              ├─ DocumentParser 解析文本
                              ├─ ChunkingService 智能分块
                              ├─ SiliconFlowEmbeddingService 向量化
                              └─ ChromaDBService 写入 ChromaDB

用户提问 → QueryRewriterService 查询重写
        → ChromaDBService 多查询并行召回 (candidateSize=20)
        → RRF 融合 (K=60)
        → SiliconFlowRerankService Cross-Encoder 精排 (topK=5)
        → 注入 LLM 上下文 (含 prompt_template 模板)
```

### 2.2 核心模块

#### 2.2.1 数据模型

**knowledge_bases** — 知识库元数据

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 主键 |
| name | VARCHAR(200) | 知识库名称 |
| description | VARCHAR(1000) | 描述 |
| user_id | BIGINT | 所属用户 |
| visibility | VARCHAR(10) | 可见性 (PRIVATE) |
| doc_count | INT | 文档数量 |
| chunk_count | INT | 分块总数 |
| total_size | BIGINT | 总存储大小 (字节) |
| prompt_template | VARCHAR(2000) | 自定义回答模板，支持 `{context}` / `{query}` 占位符 |
| chunk_size | INT | 分块大小 (默认 500) |
| chunk_overlap | INT | 分块重叠 (默认 50) |

**kb_documents** — 文档元数据

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 主键 |
| kb_id | BIGINT FK | 所属知识库 |
| file_name | VARCHAR(500) | 原始文件名 |
| file_type | VARCHAR(20) | 文件类型 (txt/md/csv) |
| file_size | BIGINT | 文件大小 |
| s3_key | VARCHAR(1000) | 本地存储路径 |
| status | VARCHAR(20) | 状态: PROCESSING / READY / ERROR |
| chunk_count | INT | 已生成分块数 |
| error_msg | VARCHAR(2000) | 错误信息 |

#### 2.2.2 文本分块 (ChunkingService)

采用 **递归字符分割** 算法，优先级递减：

```
\n\n 段落分隔 → \n 换行 → 。句号 → ；分号 → ，逗号 → 硬切
```

特性：
- 支持知识库级别自定义 `chunkSize` / `chunkOverlap`，覆盖全局默认值
- 内置 Prompt Injection 过滤正则，匹配已知攻击模式并替换为 `[已过滤]`
- 全局默认值：chunk_size=500, chunk_overlap=50

#### 2.2.3 文档解析 (DocumentParser)

接口 `DocumentParser` 定义了解析器契约：
- `parse(Path file)` → 纯文本
- `supports(String fileType)` → 是否支持

| 解析器 | 支持格式 | 备注 |
|--------|---------|------|
| TxtParser | .txt, .md, .csv | 最大解析 5MB，超出截断 |
| (已移除) | .pdf, .docx, .xlsx, .pptx, .html, 图片 | 在历史迭代中精简 |

#### 2.2.4 混合检索 (KbRetrievalService)

三阶段检索管线：

**Phase 0 — 查询重写 (可选)**

由 `QueryRewriterService` 调用 LLM 将用户口语化提问改写为 2-3 个正式检索表述，保留原始查询。由配置项 `rag.retrieve.query-rewrite-enabled` 控制开关。

**Phase 1 — 多查询并行向量召回**

对原始查询 + 各变体并行调用 ChromaDB 语义检索，每路取 `candidateSize=20` 条候选。

**Phase 2 — RRF 融合**

Reciprocal Rank Fusion (K=60) 融合多查询结果，公式：

```
RRF_score(d) = Σ 1 / (K + rank_i(d))
```

**Phase 3 — Cross-Encoder 精排**

调用 SiliconFlow `BAAI/bge-reranker-v2-m3` 模型对候选集精排，取 topK=5 条。失败时自动降级为 RRF 结果。

#### 2.2.5 嵌入与精排服务

| 服务 | 模型 | 维度 | 用途 |
|------|------|------|------|
| SiliconFlowEmbeddingService | `BAAI/bge-large-zh-v1.5` | 1024 | 文本 → 向量，批量 32 条/次 |
| SiliconFlowRerankService | `BAAI/bge-reranker-v2-m3` | Cross-Encoder | 候选精排，返回相关性分数 |

#### 2.2.6 限制措施

| 限制项 | 值 | 目的 |
|--------|-----|------|
| 单文件最大 | 20 MB | 防止大文件 OOM |
| 单文档最大分块数 | 500 | 控制单文档索引成本 |
| 单知识库最大文档数 | 200 | 控制单知识库规模 |
| 单用户文档总数 | 1000 | 控制用户级存储 |
| 单用户总存储 | 500 MB | 存储配额 |

#### 2.2.7 API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/kb/create` | 创建知识库 |
| GET | `/api/kb/list` | 用户知识库列表 |
| PUT | `/api/kb/{id}` | 编辑知识库 (名称/描述/模板/分块参数) |
| DELETE | `/api/kb/{id}` | 删除知识库及全部向量数据 |
| POST | `/api/kb/{kbId}/docs/upload` | 上传文档 |
| GET | `/api/kb/{kbId}/docs` | 文档列表 |
| DELETE | `/api/kb/docs/{docId}` | 删除文档及向量 |
| POST | `/api/kb/docs/{docId}/reindex` | 重新索引 (增量，仅更新变更分块) |

#### 2.2.8 上下文注入

在 `MessageContextBuilder.buildMessagesArray()` 中，知识库检索结果在以下位置注入 LLM 上下文：

```
1. 系统规则
2. 自定义提示词
3. 长期记忆
4. 对话摘要
5. ★ 知识库检索结果 (含 prompt_template 模板渲染)
6. 历史消息 (最近 30 条)
7. 图片/文件引用
8. 当前用户消息
```

支持知识库级 `prompt_template` 自定义回答风格，使用 `{context}` 和 `{query}` 占位符；无模板时使用默认提示词，结果附带 `file_name` 来源标注。

## 三、记忆系统

### 3.1 三层记忆模型

记忆系统模拟人类记忆的 **短期 → 中期 → 长期** 衰减规律：

```
┌─────────────────────────────────────────────────┐
│  第一层：短期记忆                                  │
│  chat_messages 表，最近 30 条对话直接注入 LLM        │
├─────────────────────────────────────────────────┤
│  第二层：中期记忆                                  │
│  conversation_summaries 表，LLM 增量摘要            │
│  触发条件：对话超过 20 轮，后续每 10 轮增量          │
├─────────────────────────────────────────────────┤
│  第三层：长期记忆                                  │
│  memory_items (MySQL) + ChromaDB (向量)           │
│  + 知识图谱 (memory_entities/relations)           │
│  自动提取 + 手动添加 + 懒衰减机制                    │
└─────────────────────────────────────────────────┘
```

### 3.2 四种操作模式

| 模式 | 方法 | 触发时机 | 说明 |
|------|------|---------|------|
| **自动提取** | `extractAndStore()` | 每次对话完成后异步 | LLM 提取事实 → 去重 (score>0.85 跳过) → 双写 ChromaDB+MySQL → 知识图谱链接 → 时态冲突检测 |
| **默认注入** | `getRecentMemoriesForContext()` | 每次构建上下文时 | 取最近 20 条 ACTIVE 记忆 (FULL+BRIEF)，按 lastAccessedAt 倒序，支持 promptId 角色隔离 |
| **按需回溯** | `searchAndRecall()` | 用户主动搜索 | 混合检索 → 恢复衰减记忆 (从 originalValue 恢复) |
| **懒衰减** | `checkAndApplyDecay()` | 读取记忆时实时检查 | 阶梯衰减，MANUAL 记忆豁免，SUPERSEDED 免衰减 |

### 3.3 懒衰减阶梯

衰减在记忆被读取时实时判定，分摊计算成本：

```
FULL (完整) ──3天未访问──→ BRIEF (简要，200字) ──7天──→ TITLE (标题，50字) ──14天──→ 遗忘删除
                                                    │                    │
                                              LLM 智能压缩          LLM 智能压缩
                                              异步执行              异步执行
```

- **FULL**：完整记忆文本
- **BRIEF**：先截断至 200 字符即时返回，再异步调用 LLM 生成智能摘要覆盖
- **TITLE**：先截断至 50 字符，再异步调用 LLM 生成标题
- **遗忘**：删除 ChromaDB 向量 + MySQL 记录
- MANUAL (用户手动添加) 记忆永远不衰减
- SUPERSEDED (被替代) 记忆跳过衰减检查

### 3.4 知识图谱 (GraphMemoryService)

从记忆事实中自动构建用户专属知识图谱：

```
用户对话 → LLM 提取三元组 (主语, 谓词, 宾语)
         → memory_entities (PERSON / ORG / LOCATION / PRODUCT / MISC)
         → memory_relations (有向边，含置信度)
         → memory_item_entities (记忆-实体关联，含 SUBJECT/OBJECT 角色)
```

核心能力：

| 功能 | 方法 | 说明 |
|------|------|------|
| **事实链接** | `linkMemory()` | 从事实文本提取三元组，建立实体/关系 |
| **图扩展检索** | `expandViaGraph()` | 记忆→实体→邻接记忆→邻接实体，1 跳扩展 |
| **反向边** | 高频谓词映射 | `工作于`↔`拥有员工`、`位于`↔`包含` 等自动追加 |
| **实体消歧** | `suggestMerges()` + `mergeEntities()` | LLM 扫描合并候选，事务内原子执行 |
| **级联失效** | `unlinkMemory()` / `expireRelations()` | 记忆被替代时自动失效关联关系 |

### 3.5 混合检索 (HybridRetrievalService)

记忆检索采用双路并行 + 融合 + 精排架构：

```
Phase 1: 两路并行召回
  ├─ ChromaDB 语义向量检索 (30 条候选)
  └─ 知识图谱实体匹配 (EntityRetrievalService)
       └─ LLM 提取专有名词 → 匹配实体库 → 聚合关联记忆 → 图扩展邻接实体 (score=0.5)

Phase 2: RRF 融合 (K=60)

Phase 3: Cross-Encoder 精排 (topK=10)
  └─ 失败降级返回 RRF 结果
```

### 3.6 时态冲突检测

当新记忆与旧记忆语义相似 (score 0.75-0.90) 时触发：
1. ChromaDB 搜索语义相似的旧记忆
2. LLM 判定是否构成事实冲突 (如 "住在北京" vs "住在上海")
3. 旧记忆标记为 SUPERSEDED，级联失效知识图谱关系

### 3.7 角色隔离

通过 `memory_items.prompt_id` 字段实现提示词级别记忆隔离：
- NULL：共享记忆，所有角色可见
- 非 NULL：仅对应 prompt 角色可见

### 3.8 对话摘要 (SummaryService)

增量摘要生成策略：

| 参数 | 值 | 说明 |
|------|-----|------|
| 首次触发 | 20 轮 | 对话达到 20 轮时生成首次摘要 |
| 增量刷新 | 10 轮 | 后续每新增 10 轮增量更新摘要 |
| 保留最近 | 10 条 | 最近 10 条消息不参与摘要，保留细节 |

### 3.9 API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/memory/list` | 所有记忆列表 |
| GET | `/api/memory/enabled` | 已启用记忆 |
| POST | `/api/memory/add` | 手动添加记忆 (最大 2000 字符) |
| PUT | `/api/memory/{id}` | 编辑记忆 |
| PUT | `/api/memory/{id}/toggle` | 启用/禁用 |
| DELETE | `/api/memory/{id}` | 删除单条记忆 |
| DELETE | `/api/memory/clear` | 清空全部记忆 |
| POST | `/api/memory/search` | 混合检索 (模式3) |
| GET | `/api/memory/entities/merge-suggestions` | 实体消歧建议 |
| POST | `/api/memory/entities/merge` | 执行实体合并 |

## 四、基础设施与共享服务

### 4.1 ChromaDB

- 嵌入式向量数据库，由 `ChromaDBLauncher` 在应用启动时自动检测并拉起子进程，关闭时自动销毁
- 通过 HTTP API (V2) 交互，封装在 `BaseChromaDBService<T>` 抽象基类中
- 两个子类通过不同 Collection 命名实现隔离：

| 子类 | 泛型参数 | Collection 命名 | 用途 |
|------|---------|----------------|------|
| ChromaDBService | Long | `kb_{kbId}` | 知识库向量 |
| MemoryChromaService | Long | `mem_{userId}` | 记忆向量 |

### 4.2 嵌入与精排 (SiliconFlow API)

| 服务 | 模型 | 维度 | 批量 |
|------|------|------|------|
| Embedding | `BAAI/bge-large-zh-v1.5` | 1024 | 32/批 |
| Rerank | `BAAI/bge-reranker-v2-m3` | Cross-Encoder | 无批量限制 |

### 4.3 配置属性总览

| 配置类 | 关键属性 | 默认值 |
|--------|---------|--------|
| RagProperties | chunk.size | 500 |
| | chunk.overlap | 50 |
| | retrieve.topK | 5 |
| | retrieve.candidateSize | 20 |
| | retrieve.queryRewriteEnabled | true |
| MemoryProperties | inject.recentCount | 20 |
| | searchTopK | 10 |
| | decay.freshDays | 3 |
| | decay.briefDays | 7 |
| | decay.forgetDays | 14 |
| SummaryProperties | triggerThreshold | 20 |
| | refreshThreshold | 10 |
| | keepRecent | 10 |

### 4.4 异步处理

| 线程池 | core | max | queue | 策略 | 用途 |
|--------|------|-----|-------|------|------|
| kbProcessExecutor | 1 | 2 | 20 | CallerRunsPolicy | 文档处理管线 |

`ChatPostProcessor` 在每次对话完成后异步触发：
1. `MemoryService.extractAndStore()` — 自动提取记忆
2. `SummaryService.checkAndGenerate()` — 增量摘要生成

## 五、预期容量分析

### 5.1 知识库容量

**单知识库维度：**

| 指标 | 上限 | 计算依据 |
|------|------|---------|
| 文档数 | 200 个 | `MAX_DOCS_PER_KB` |
| 分词块总数 | ~100,000 | 200 文档 × 500 块/文档 (max) |
| 存储量 | ~500 MB | 假设平均 2.5MB/文档 |
| 向量维度 | 1024 | bge-large-zh-v1.5 |
| 单知识库向量数据量 | ~390 MB | 100,000 × 1024 × 4 bytes |

**单用户维度：**

| 指标 | 上限 | 计算依据 |
|------|------|---------|
| 文档总数 | 1000 个 | `MAX_TOTAL_DOCS_PER_USER` |
| 总存储 | 500 MB | `MAX_TOTAL_STORAGE_PER_USER` |
| 知识库数 | 无硬限制 | 仅受文档数和存储配额间接约束 |

**系统级 (单实例，本地 ChromaDB)：**

| 指标 | 预估值 | 说明 |
|------|--------|------|
| 最大 Collection 数 | ~10,000 | ChromaDB 单实例经验值 |
| 推荐用户数 | 100-500 | 取决于文档上传频率和并发量 |
| 单次文档处理耗时 | 2-10 秒 | 解析 + 分块 + Embedding API 调用 |

### 5.2 记忆容量

**单用户维度：**

| 指标 | 预估值 | 说明 |
|------|--------|------|
| 活跃记忆数 | ~500-2000 条 | 受衰减机制自然调控 |
| 记忆实体数 | ~100-500 个 | 知识图谱提取累积 |
| 实体关系数 | ~200-2000 条 | 与记忆数和实体数正相关 |
| 对话摘要数 | ~1-5 个/会话 | 增量摘要 |

**衰减机制自然调控：**

在不活跃的情况下，用户记忆将在 14 天内自动衰减至遗忘。活跃用户持续对话会不断刷新 `lastAccessedAt`，保持记忆存留。

### 5.3 向量存储总量估算

以 500 用户、平均每用户 2 个知识库、500 条记忆计算：

| 存储项 | 单条向量 | 数量 | 总量 |
|--------|---------|------|------|
| 知识库 Chunk | 1024 × 4B = 4KB | 500用户 × 2KB × 500块 ≈ 500K | ~2 GB |
| 记忆条目 | 1024 × 4B = 4KB | 500用户 × 500条 = 250K | ~1 GB |
| **合计** | | | **~3 GB** |

> 注：以上为向量裸数据估算，ChromaDB 实际占用约 1.2-1.5x (含索引和元数据)，即 **3.6-4.5 GB**。

## 六、预期效果分析

### 6.1 知识库问答效果

| 效果维度 | 预期表现 | 支撑机制 |
|---------|---------|---------|
| **检索精度** | Top-5 命中率 > 85% | RRF 融合 + Cross-Encoder 精排 |
| **多角度覆盖** | 显著优于单查询检索 | QueryRewriter 生成 2-3 个变体并行召回 |
| **抗噪能力** | 精排后噪声率 < 15% | bge-reranker-v2-m3 直接计算 query-doc 语义相关度 |
| **回答可控性** | 按知识库定制风格 | prompt_template 支持 `{context}` / `{query}` 占位符 |
| **来源可追溯** | 100% 附带来源 | 检索结果注入 `file_name` 标注 |

### 6.2 记忆系统效果

| 效果维度 | 预期表现 | 支撑机制 |
|---------|---------|---------|
| **跨会话连续性** | 用户偏好/事实跨会话可追溯 | ChromaDB 持久化 + 每次上下文默认注入 20 条 |
| **信息密度** | 去重率 > 90% | 相似度 0.85 阈值过滤 |
| **时效性** | 过时事实自动淘汰 | 3/7/14 天阶梯衰减 |
| **事实一致性** | 冲突自动解决 | 时态冲突检测 + SUPERSEDED 机制 |
| **关联发现** | 实体间隐含关系可检索 | 知识图谱 1 跳扩展 + 实体检索 |
| **存储效率** | 不活跃记忆 14 天自动清理 | 懒衰减机制，零维护成本 |

### 6.3 性能表现

| 场景 | 耗时 (P50) | 耗时 (P95) | 瓶颈 |
|------|-----------|-----------|------|
| 知识库检索 (无重写) | ~500ms | ~1.2s | ChromaDB + Embedding API |
| 知识库检索 (含重写) | ~1.5s | ~3.5s | LLM 查询重写 |
| 记忆检索 | ~400ms | ~1.0s | ChromaDB + Rerank API |
| 记忆自动提取 (异步) | 不阻塞 | 后台 2-5s | LLM 事实提取 |
| 文档处理 (5MB txt) | ~3s | ~8s | Embedding API 批量调用 |

### 6.4 架构优势

1. **低成本**：ChromaDB 嵌入式部署零运维，SiliconFlow API 按量付费，无需自建 GPU
2. **高内聚**：知识库和记忆共享底层向量和精排基础设施，减少重复建设
3. **可观测**：所有检索结果含分数，支持调试和效果评估
4. **容错设计**：Rerank 失败降级 RRF，任一路召回失败不影响整体
5. **渐进式衰减**：记忆自然淘汰，无需人工清理，MANUAL 记忆永久保留
